# MarketRadar

SaaS для продавцов маркетплейсов. Регистрируетесь, подключаете API-токен Wildberries —
сервис сам сравнивает вашу цену с ценой на сайте и считает текущий СПП по каждому
товару, копит историю и показывает, что на неё похоже влияет. Дальше в продукт
по очереди добавляются ещё четыре модуля (см. «Роадмап» ниже).

## Что уже полностью работает

- Регистрация/вход, у каждого продавца — свой отдельный кабинет и свои данные.
- Подключение API-токена Wildberries (хранится в базе в зашифрованном виде).
- Синхронизация: тянет все товары продавца и их цену через официальный API
  Wildberries «Цены и скидки», сверяет с текущей ценой на сайте, считает СПП.
- История по каждому товару (график) и общая аналитика по факторам: тренд по
  дням, разбивка по дню недели, разбивка по цене товара, топ движений СПП.

Формула СПП — та же, что и в первой версии, максимально простая:

```
СПП% = (цена_продавца − цена_на_сайте) / цена_продавца × 100
```

## Локальный запуск

Нужен Node.js 18+ и Postgres (локально или в Docker).

```bash
npm install
npx playwright install --with-deps chromium   # нужен для получения цены на сайте
cp .env.example .env
# укажите в .env DATABASE_URL, SESSION_SECRET, APP_SECRET и (опционально) RESIDENTIAL_PROXIES
npm start
```

Без `RESIDENTIAL_PROXIES` в `.env` сервис всё равно запустится и будет нормально
синхронизировать цену продавца — просто «Цена на сайте»/«СПП» останутся пустыми
(см. README → «Откуда берутся две цены»).

Таблицы создаются автоматически при первом запуске (`migrate()` в `server.js`).
Откройте `http://localhost:3000`, зарегистрируйтесь, вставьте свой API-токен
Wildberries (личный кабинет продавца → Настройки → Доступ к API → создать токен
с правами на категорию **«Цены и скидки»**, доступ на чтение).

## Деплой на Render

Сервис теперь деплоится через Docker (`Dockerfile` в корне репозитория) — обычный
Node-рантайм Render не подходит, потому что получению цены на сайте нужен настоящий
Chromium (Playwright) со всеми его системными библиотеками, а для этого в процессе
сборки нужен root/apt-get, которого в обычном Node-окружении Render нет. `render.yaml`
уже настроен на `runtime: docker` и сам создаёт веб-сервис и managed Postgres.

**Если в этом чате подключён коннектор Render** — просто попросите продолжить, и
сервис будет создан и задеплоен прямо отсюда.

**Вручную, через сайт Render:**
1. Загрузите этот репозиторий в свой GitHub/GitLab.
2. В Render: New → Blueprint → укажите репозиторий. Render прочитает `render.yaml`
   и предложит создать веб-сервис `marketradar` (Docker) и базу `marketradar-db`.
3. Подтвердите — `SESSION_SECRET` и `APP_SECRET` Render сгенерирует сам
   (`generateValue: true` в блюпринте), `DATABASE_URL` подставит из созданной базы.
4. **Отдельно, вручную** (блюпринт не подставляет секреты за вас) — в Render →
   ваш сервис → Environment добавьте `RESIDENTIAL_PROXIES` со своими прокси
   (формат — в `.env.example`). Без этого шага цена продавца будет работать,
   а цена на сайте/СПП — нет.
5. Первый деплой на Docker дольше обычного (собирает Chromium) — это нормально.
6. После деплоя откройте выданный Render URL — это и есть ваш онлайн-сервис.

## Откуда берутся две цены

**Цена продавца.** Официальный, документированный эндпоинт Wildberries для продавцов:
`GET https://discounts-prices-api.wildberries.ru/api/v2/list/goods/filter`
(заголовок `Authorization: <токен продавца>`).

**Цена на сайте** (то, что реально видит покупатель — после скидки продавца и после
СПП) — самая сложная часть проекта, через несколько тупиковых веток. По порядку, что
было проверено вживую и не сработало:

1. Голый HTTP-запрос к внутреннему эндпоинту карточки товара (`card.wb.ru`, позже —
   `www.wildberries.ru/__internal/u-card/...`) — что с сервера, что с браузера продавца.
   В 2026 году Wildberries поставила перед этими данными настоящую антибот-проверку
   (JS-челлендж): голый запрос получает HTTP 498 с заглушкой вместо цены — не помогают
   ни правильные заголовки, ни CORS-обходы.
2. Готовый сторонний API (пробовали WBCON/apiportal.ru) — умеет отдавать цену, но
   оказался неточным (разошёлся с реальной ценой на ~2% в проверке) и это чужой,
   непрозрачный конвейер, за который сервис ответственности не несёт.
3. Обычный дата-центровый прокси, даже дорогой «stealth»-уровень (пробовали
   ScrapingBee) — проходит JS-антибот, но Wildberries отдельно, по репутации IP,
   помечает дата-центровые адреса как VPN и вместо карточки товара отдаёт главную
   страницу сайта (в ответе буквально есть `<div id="blockedVpn">`).

**Что в итоге работает** (проверено вживую на реальном товаре): настоящий IP
российского мобильного оператора + настоящий браузер, который сам честно проходит
антибот-проверку. Реализовано в `src/priceScraper.js` через Playwright (управляемый
Chromium): сервис открывает страницу товара `wildberries.ru/catalog/<nmId>/detail.aspx`
за резидентным/мобильным прокси и перехватывает внутренний ответ с ценой, который сама
страница подгружает после успешного прохождения проверки — вместо того чтобы бить по
этому эндпоинту напрямую (без сессии/куки антибота он тоже заблокирован).

Продавцу по-прежнему ничего не нужно вводить или настраивать — прокси и браузер
работают на сервере, невидимо для клиента, при нажатии «Синхронизировать сейчас».

### ⚠️ Что важно понимать про эту часть

- **Нужен как минимум один резидентный/мобильный прокси-IP.** Без него эта часть просто
  не работает — колонки «Цена на сайте»/«СПП» останутся пустыми, а цена продавца
  синхронизируется как обычно. Прокси покупает оператор сервиса (вы) у стороннего
  провайдера (в разработке использовался LTE.Center — российские мобильные IP от 600
  ₽/мес за один, есть и другие похожие сервисы) и прописывает в переменную окружения
  `RESIDENTIAL_PROXIES` на Render (формат — в `.env.example`). **Не подходит обычный
  дата-центровый/«для парсинга» прокси** — он будет помечен как VPN, см. пункт 3 выше.
- Это ощутимо медленнее одного HTTP-запроса: на каждый товар — полноценная загрузка
  страницы в браузере плюс пауза `SCRAPE_DELAY_MS` (по умолчанию ~5 сек), чтобы не
  выглядеть ботом для антифрод-системы Wildberries. Для каталога в несколько десятков
  товаров синхронизация может занимать несколько минут — это ожидаемо. При нескольких
  прокси в `RESIDENTIAL_PROXIES` сервис меняет их по очереди (`SCRAPE_ROTATE_EVERY`).
  Не запускайте параллельно ручную синхронизацию и проверку того же прокси в обычном
  браузере — Wildberries может расценить два разных «отпечатка» с одного IP в одно
  время как явный признак бота (проверено вживую).
- Это не официальный канал Wildberries — сама механика антибот-защиты может измениться
  без предупреждения. Если это случится, чинить нужно `src/priceScraper.js`; сама
  СПП-математика (`computeSppPercent` в `wbClient.js`) и вставка снимков в
  `syncService.js` от способа получения цены не зависят.
- **Цена в `<title>` страницы ненадёжна.** Проверено вживую: `<title>` показывал
  референсную цену без учёта временной акции (2740 ₽), когда реальная цена с флеш-акцией
  была ниже (2685 ₽) — поэтому `priceScraper.js` берёт цену из перехваченного JSON, а не
  из текста страницы.
- Цена берётся с точки зрения обычного, не залогиненного покупателя. Реальный СПП может
  быть персонализированным для конкретного человека — число в дашборде надёжный
  **ориентир по рынку**, а не гарантированно точная скидка для каждого покупателя.

## SaaS-скелет: тарифы и лимиты

Таблица `users` уже содержит поля `plan`, `plan_status` и `sku_limit` — при
синхронизации сервис не тянет больше товаров, чем разрешает `sku_limit` (по
умолчанию 100), и сообщает, сколько пропущено. Это заготовка под реальные тарифы:
биллинга (приём платежей) пока нет — его стоит подключать отдельным шагом, когда
определитесь с провайдером (ЮKassa/CloudPayments для российских карт, Stripe — для
зарубежных). Роль `role = 'admin'` зарезервирована под будущую админку
(изменение тарифа/лимита вручную, пока без интерфейса — через прямой SQL-запрос
к базе:
`UPDATE users SET plan = 'pro', sku_limit = 1000 WHERE email = '...';`).

## Роадмап (по одному модулю за раз)

| Модуль | Статус |
|---|---|
| История и факторы СПП (Wildberries) | ✅ готово |
| Юнит-экономика | заглушка в интерфейсе, план — в `public/unit-economics.html` |
| Перенос карточек между маркетплейсами | заглушка, план — в `public/card-transfer.html` |
| Генерация этикеток | заглушка, план — в `public/labels.html` |
| Генерация контента для карточек (ИИ) | заглушка, план — в `public/content.html` |

СПП пока считается только для Wildberries. Схема БД специально сделана так, чтобы
добавить Ozon (Соинвест) и Яндекс Маркет без переделки остального: понадобится
таблица учётных данных по каждой площадке и колонка `marketplace` в снимках цен.

## Структура проекта

```
server.js                 — точка входа, Express, сессии в Postgres
src/db.js                 — пул Postgres, миграция схемы при старте
src/crypto.js             — шифрование сохранённого API-токена (AES-256-GCM)
src/wbClient.js           — официальный API Wildberries (цена продавца)
src/priceScraper.js       — цена на сайте: Playwright + резидентный/мобильный прокси
src/syncService.js        — полный цикл синхронизации одного пользователя
src/asyncHandler.js        — обёртка для async-роутов Express 4
src/routes/auth.js        — регистрация/вход/выход
src/routes/wb.js          — токен, синхронизация, товары, история, факторы
Dockerfile                — сборка для Render (Node + Chromium/Playwright)
render.yaml               — Render Blueprint (Docker веб-сервис + managed Postgres)
public/                   — фронтенд (html/css/js без сборки)
public/js/nav.js          — общая навигация и проверка авторизации на всех страницах
public/js/charts.js       — линейный и столбчатый графики на чистом SVG
```

## Проверка перед продакшеном

Все SQL-запросы (миграция схемы, апсерт токена, история, факторы) прогнаны вручную
через локальный Postgres 16 с тестовыми данными — синтаксис и логика подтверждены.
Весь JS проверен на синтаксис (`node --check`). Сама механика получения цены на сайте
(мобильный прокси + честный браузер) проверена **вживую, но вручную**: обычный Chrome
за прокси LTE.Center реально показал настоящую карточку товара с настоящей ценой без
блокировки — это и есть доказательство, что подход рабочий. А вот сам код в
`src/priceScraper.js` (Playwright) через `npm install`/живой запуск проверить не
удалось — в среде, где это писалось, нет доступа ни к npm-реестру, ни к произвольным
внешним IP (в том числе к самому прокси). Обязательно прогоните `npm install && npm
start` (или соберите `Dockerfile` и задеплойте) у себя перед первым реальным
использованием и убедитесь, что регистрация, подключение токена и полная
синхронизация (обе цены) проходят на вашем аккаунте с вашим прокси.

## Известные ограничения

- Для товаров с ценами по размерам (`editableSizePrice: true`) берётся цена только
  первого размера.
- Автосинхронизация (`AUTO_SYNC_MINUTES`) — простой `setInterval` в процессе, с защитой
  от наложения проходов друг на друга (см. `server.js`), но всё ещё синхронизирует
  пользователей по одному, последовательно. При росте числа пользователей и с учётом
  того, что получение цены на сайте теперь идёт через браузер (медленно, см.
  `src/priceScraper.js`), стоит вынести это в отдельный воркер с очередью.
- Один резидентный/мобильный прокси даёт один параллельный поток получения цены на
  сайте — с ростом числа пользователей и товаров понадобится больше прокси в
  `RESIDENTIAL_PROXIES` (провайдеры вроде LTE.Center продают их поштучно) и, возможно,
  несколько параллельных браузерных воркеров вместо одного последовательного цикла.
- Биллинга нет — есть только поля под тарифы и мягкий лимит по количеству товаров.
- Пароли и токены пользователей — зона повышенной ответственности: не публикуйте
  `.env` и не логируйте токены; на Render база и сервис уже общаются по приватной сети.
